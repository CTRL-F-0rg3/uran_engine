1/*! Allocating resource ids, and tracking the resources they refer to.
2
3The `wgpu_core` API uses identifiers of type [`Id<R>`] to refer to
4resources of type `R`. For example, [`id::DeviceId`] is an alias for
5`Id<Device<Empty>>`, and [`id::BufferId`] is an alias for
6`Id<Buffer<Empty>>`. `Id` implements `Copy`, `Hash`, `Eq`, `Ord`, and
7of course `Debug`.
8
9Each `Id` contains not only an index for the resource it denotes but
10also a Backend indicating which `wgpu` backend it belongs to. You
11can use the [`gfx_select`] macro to dynamically dispatch on an id's
12backend to a function specialized at compile time for a specific
13backend. See that macro's documentation for details.
14
15`Id`s also incorporate a generation number, for additional validation.
16
17The resources to which identifiers refer are freed explicitly.
18Attempting to use an identifier for a resource that has been freed
19elicits an error result.
20
21## Assigning ids to resources
22
23The users of `wgpu_core` generally want resource ids to be assigned
24in one of two ways:
25
26- Users like `wgpu` want `wgpu_core` to assign ids to resources itself.
27  For example, `wgpu` expects to call `Global::device_create_buffer`
28  and have the return value indicate the newly created buffer's id.
29
30- Users like `player` and Firefox want to allocate ids themselves, and
31  pass `Global::device_create_buffer` and friends the id to assign the
32  new resource.
33
34To accommodate either pattern, `wgpu_core` methods that create
35resources all expect an `id_in` argument that the caller can use to
36specify the id, and they all return the id used. For example, the
37declaration of `Global::device_create_buffer` looks like this:
38
39```ignore
40impl<G: GlobalIdentityHandlerFactory> Global<G> {
41    /* ... */
42    pub fn device_create_buffer<A: HalApi>(
43        &self,
44        device_id: id::DeviceId,
45        desc: &resource::BufferDescriptor,
46        id_in: Input<G, id::BufferId>,
47    ) -> (id::BufferId, Option<resource::CreateBufferError>) {
48        /* ... */
49    }
50    /* ... */
51}
52```
53
54Users that want to assign resource ids themselves pass in the id they
55want as the `id_in` argument, whereas users that want `wgpu_core`
56itself to choose ids always pass `()`. In either case, the id
57ultimately assigned is returned as the first element of the tuple.
58
59Producing true identifiers from `id_in` values is the job of an
60[`crate::identity::IdentityManager`], but only if the `IdentityHandlerFactory`
61create it and then generated by it, otherwise ids will be received from outside.
62
63`Global::new` expects a `factory` argument that
64implements the [`GlobalIdentityHandlerFactory`] trait, which extends
65[`crate::identity::IdentityHandlerFactory<I>`] for each resource id type `I`. This
66trait, in turn, has a `spawn` method that constructs an
67`crate::identity::IdentityManager` for the `Global` to use,
68if ids should be generated by wgpu or will return None otherwise.
69
70## Id allocation and streaming
71
72Perhaps surprisingly, allowing users to assign resource ids themselves
73enables major performance improvements in some applications.
74
75The `wgpu_core` API is designed for use by Firefox's [WebGPU]
76implementation. For security, web content and GPU use must be kept
77segregated in separate processes, with all interaction between them
78mediated by an inter-process communication protocol. As web content uses
79the WebGPU API, the content process sends messages to the GPU process,
80which interacts with the platform's GPU APIs on content's behalf,
81occasionally sending results back.
82
83In a classic Rust API, a resource allocation function takes parameters
84describing the resource to create, and if creation succeeds, it returns
85the resource id in a `Result::Ok` value. However, this design is a poor
86fit for the split-process design described above: content must wait for
87the reply to its buffer-creation message (say) before it can know which
88id it can use in the next message that uses that buffer. On a common
89usage pattern, the classic Rust design imposes the latency of a full
90cross-process round trip.
91
92We can avoid incurring these round-trip latencies simply by letting the
93content process assign resource ids itself. With this approach, content
94can choose an id for the new buffer, send a message to create the
95buffer, and then immediately send the next message operating on that
96buffer, since it already knows its id. Allowing content and GPU process
97activity to be pipelined greatly improves throughput.
98
99To help propagate errors correctly in this style of usage, when resource
100creation fails, the id supplied for that resource is marked to indicate
101as much, allowing subsequent operations using that id to be properly
102flagged as errors as well.
103
104[`gfx_select`]: crate::gfx_select
105[`Input`]: crate::identity::IdentityHandlerFactory::Input
106[`process`]: crate::identity::IdentityManager::process
107[`Id<R>`]: crate::id::Id
108[wrapped in a mutex]: trait.IdentityHandler.html#impl-IdentityHandler%3CI%3E-for-Mutex%3CIdentityManager%3E
109[WebGPU]: https://www.w3.org/TR/webgpu/
110
111*/

155/// All the resources for a particular backend in a [`crate::global::Global`].
156///
157/// To obtain `global`'s `Hub` for some [`HalApi`] backend type `A`,
158/// call [`A::hub(global)`].
159///
160/// ## Locking
161///
162/// Each field in `Hub` is a [`Registry`] holding all the values of a
163/// particular type of resource, all protected by a single RwLock.
164/// So for example, to access any [`Buffer`], you must acquire a read
165/// lock on the `Hub`s entire buffers registry. The lock guard
166/// gives you access to the `Registry`'s [`Storage`], which you can
167/// then index with the buffer's id. (Yes, this design causes
168/// contention; see [#2272].)
169///
170/// But most `wgpu` operations require access to several different
171/// kinds of resource, so you often need to hold locks on several
172/// different fields of your [`Hub`] simultaneously.
173///
174/// Inside the `Registry` there are `Arc<T>` where `T` is a Resource
175/// Lock of `Registry` happens only when accessing to get the specific resource
176///
177///
178/// [`A::hub(global)`]: HalApi::hub
179pub struct Hub<A: HalApi> {
180    pub adapters: Registry<id::AdapterId, Adapter<A>>,
181    pub devices: Registry<id::DeviceId, Device<A>>,
182    pub queues: Registry<id::QueueId, Queue<A>>,
183    pub pipeline_layouts: Registry<id::PipelineLayoutId, PipelineLayout<A>>,
184    pub shader_modules: Registry<id::ShaderModuleId, ShaderModule<A>>,
185    pub bind_group_layouts: Registry<id::BindGroupLayoutId, BindGroupLayout<A>>,
186    pub bind_groups: Registry<id::BindGroupId, BindGroup<A>>,
187    pub command_buffers: Registry<id::CommandBufferId, CommandBuffer<A>>,
188    pub render_bundles: Registry<id::RenderBundleId, RenderBundle<A>>,
189    pub render_pipelines: Registry<id::RenderPipelineId, RenderPipeline<A>>,
190    pub compute_pipelines: Registry<id::ComputePipelineId, ComputePipeline<A>>,
191    pub query_sets: Registry<id::QuerySetId, QuerySet<A>>,
192    pub buffers: Registry<id::BufferId, Buffer<A>>,
193    pub staging_buffers: Registry<id::StagingBufferId, StagingBuffer<A>>,
194    pub textures: Registry<id::TextureId, Texture<A>>,
195    pub texture_views: Registry<id::TextureViewId, TextureView<A>>,
196    pub samplers: Registry<id::SamplerId, Sampler<A>>,
197}

222    //TODO: instead of having a hacky `with_adapters` parameter,
223    // we should have `clear_device(device_id)` that specifically destroys
224    // everything related to a logical device.
225    pub(crate) fn clear(
226        &self,
227        surface_guard: &Storage<Surface, id::SurfaceId>,
228        with_adapters: bool,
229    ) {
230        use hal::Surface;
231
232        let mut devices = self.devices.write();
233        for element in devices.map.iter() {
234            if let Element::Occupied(ref device, _) = *element {
235                device.prepare_to_die();
236            }
237        }
238
239        self.command_buffers.write().map.clear();
240        self.samplers.write().map.clear();
241        self.texture_views.write().map.clear();
242        self.textures.write().map.clear();
243        self.buffers.write().map.clear();
244        self.bind_groups.write().map.clear();
245        self.shader_modules.write().map.clear();
246        self.bind_group_layouts.write().map.clear();
247        self.pipeline_layouts.write().map.clear();
248        self.compute_pipelines.write().map.clear();
249        self.render_pipelines.write().map.clear();
250        self.query_sets.write().map.clear();
251
252        for element in surface_guard.map.iter() {
253            if let Element::Occupied(ref surface, _epoch) = *element {
254                if let Some(ref mut present) = surface.presentation.lock().take() {
255                    if let Some(device) = present.device.downcast_ref::<A>() {
256                        let suf = A::get_surface(surface);
257                        unsafe {
258                            suf.unwrap().raw.unconfigure(device.raw());
259                            //TODO: we could destroy the surface here
260                        }
261                    }
262                }
263            }
264        }
265
266        self.queues.write().map.clear();
267        devices.map.clear();
268
269        if with_adapters {
270            drop(devices);
271            self.adapters.write().map.clear();
272        }
273    }
274
275    pub(crate) fn surface_unconfigure(&self, device: &Device<A>, surface: &HalSurface<A>) {
276        unsafe {
277            use hal::Surface;
278            surface.raw.unconfigure(device.raw());
279        }
280    }
